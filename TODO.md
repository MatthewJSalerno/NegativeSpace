## Durability claims: stated vs enforced

Two separate audits have caught the same failure mode — a guarantee written down more strongly than the code actually enforces. This table exists so every durability claim resolves to either **enforced and tested** or **a documented limitation**, and never sits quietly in between.

The rule: if a claim cannot be enforced, weaken the claim. Do not leave prose asserting something the code only usually does.

### Outstanding

- [x] ~~**The audit log is less durable than the act it records — on the SCAN path only.**~~ **Closed 2026-09-23: fsync at run end** (claim 12). The move/copy half was already closed by claim 10. For the scan path the two options were to accept the loss and say so, or to fsync once at run end. The fsync won because it costs one fsync per run, not per batch, and it makes a *completed* run's history durable without touching the ~4.4x. **Why not `FULL` on the scan path:** that pays the 4.4x on every batch to protect rows a re-Index reproduces anyway. What the scan path records is reading, not deleting.

- [x] ~~**`reconcile_interrupted_state` still commits at `NORMAL`.**~~ **Decided 2026-09-22: extended to `FULL`.** The "probably benign" argument rested on recovery being reproducible — lose the repair, and the next run redoes it from the same filesystem evidence. That stopped being true when recovery began recording *evidence and attention state*: those are conclusions drawn from observations that may not be repeatable, because storage disappears and files are replaced between runs. A lost repair would now discard the only record that an outcome could not be established, and silently present the next run's fresh guess as though nothing had been lost. The cost is the same order as claim 10's 1.42x on a path that runs once per interrupted row at startup, not per file.

- [ ] **Power-loss behaviour has never been tested, only reasoned about.** Every durability test asserts *which* fsyncs happen and in what order, not that a real power cut preserves the tree. That is a meaningful gap between "the barriers are in the right places" and "the guarantee holds". Options: `dm-log-writes` or device-mapper `flakey` in a VM to replay a crash at an arbitrary point, or a documented statement that it is untested here and why. **A third option, established 2026-09-17 and worth generalising:** a power cut cannot be *caused* here, but the state one *leaves behind* can be constructed directly, and the engine's response to it tested deterministically — no VM required. That is how claim 10 got its evidence: take a completed move, rewind the catalog behind it while the filesystem keeps what it did, then observe what the next run concludes. This splits the untestable question in two. **Consequence** — "given this loss, does the engine do the right thing?" — is testable today, cheaply, and is where every defect found so far has actually lived. **Mechanism** — "does `NORMAL` really lose that commit on this hardware?" — still needs the VM. Most of the value sits in the half that needs no VM, and those probes belong in the suite rather than as one-off scripts.

- [x] ~~**A destination on an NFS share exported `async` can acknowledge an fsync before data reaches the server's disk.**~~ **Closed 2026-09-23: a documented limitation**, which is this table's other valid resolution. The README's Configuration & Notes section carries it beside the existing `flock`/NFS caveat: such a share can acknowledge an `fsync` before data reaches the server's disk, the barrier chain is therefore only as good as the server's honesty about it, local disk (the tested configuration) and an NFS-mounted `--source` are unaffected since nothing is written there, and the remedy is to export the share `sync`. **The "is it worth detecting" half resolves to no, for a reason worth keeping:** an NFS client cannot see the server's export options, so `async` is invisible from where the engine sits — a successful `fsync` return is all it ever observes. There is nothing to detect and therefore nothing to test, which is why this weakens the claim rather than enforcing it.

- [ ] **Re-audit these claims whenever the write path changes.** Both defects found so far were introduced *by a fix to this very path*: the ancestor chain was added, then forgotten after the first failure. A change to `copy_verify_delete`, `_mkdir_durable`, `_finalize_partial` or `_remove_verified_source` should end with this table re-checked rather than assumed.

## Before the first release

- [ ] **Re-introduce schema versioning.** The engine deliberately does not stamp `PRAGMA user_version` or refuse a catalog written by older code. While the schema changes often and every catalog is synthetic and rebuilt on demand, the check's only practical effect is to force a delete-and-rebuild that happens anyway — and a version constant nobody remembers to bump gives false confidence rather than protection. That calculus inverts the moment real users hold catalogs they cannot casually discard. Add the stamp and the startup refusal together, against catalogs created fresh at that point; an unstamped development catalog reads as version 0 and is refused naturally, which is the correct outcome.
